Создай production-ready Telegram-бот для внутреннего учёта расходных материалов парикмахерской NEFOR SPOT.

ВАЖНО:
Это не прототип. Нужно сразу реализовать законченную, устойчивую архитектуру, потому что проект будет использоваться ежедневно мастерами салона.

Я работаю в основном с iPhone и не хочу вручную редактировать код, выполнять команды в Shell или исправлять БД после обновлений.

После выполнения задания:
1. самостоятельно проверь проект;
2. запусти тесты;
3. исправь найденные ошибки;
4. запусти приложение;
5. убедись, что Telegram-бот действительно стартует;
6. дай краткий отчёт о том, что реализовано;
7. отдельно объясни, что мне нужно сделать для постоянного production-хостинга.

5. РАЗДЕЛЕНИЕ СКЛАДСКОЙ И РАСЧЁТНОЙ ЦЕНЫ
==================================================

Это критически важно.

У каждой позиции могут существовать:

purchase_price_per_unit / purchase_price_per_gram
— реальная закупочная стоимость;

calculation_rate
— ставка, используемая при расчёте себестоимости процедуры.

Это НЕ одно и то же.

Например реальная краска может стоить 5 ₽/г, но calculation_rate может быть 8.90 ₽/г, потому что в расчётной ставке уже учтены дополнительные расходы.

Изменение закупочной цены НЕ должно автоматически менять старые расчёты.

Изменение calculation_rate НЕ должно менять старые расчёты.

Каждый завершённый calculation_item должен сохранять snapshot:
- product id;
- название на момент расчёта;
- бренд;
- категорию;
- количество;
- calculation_rate на момент расчёта;
- итоговую стоимость позиции.

==================================================
14. WHEN INVENTORY IS DEDUCTED
==================================================

CRITICAL:

DO NOT deduct inventory while user is merely building a calculation.

Deduct inventory ONLY when the calculation is finally completed.

Saving:
- calculation;
- calculation items;
- inventory movements;

must happen in ONE database transaction.

Either everything commits or everything rolls back.

A cancelled calculation must cause ZERO inventory movements.

Protect against duplicate completion / double clicking.

One Telegram calculation must not be able to deduct inventory twice.

Use an idempotency mechanism / unique completion token where appropriate.

==================================================
27. MIGRATIONS
==================================================

This is critical.

Never implement future catalog changes by:
DROP TABLE materials
and recreating it.

Create safe, versioned, forward-only migrations.

Before any potentially structural migration:
create a database backup where possible.

Migrations must be idempotent / version controlled.

Existing history must survive future updates.

Seed data must use UPSERT / stable keys and must NOT duplicate products on every restart.

Do not overwrite administrator-modified values every time the application starts.

==================================================
28. PERSISTENCE / HOSTING
==================================================

This bot must be designed to run continuously 24/7.

IMPORTANT:
Do not rely on the Replit development workspace remaining open.

Do not use browser keep-alive hacks as the primary production architecture.

The application must be hosting-independent.

Configuration through environment variables.

Support:

BOT_TOKEN
ADMIN_USER_ID
DATABASE_PATH or DATABASE_URL
APP_ENV
LOG_LEVEL

If SQLite is used, database path must be on persistent storage.

Do NOT assume an ephemeral deployment filesystem safely stores the business database.

Provide a clean abstraction so storage can later migrate to PostgreSQL without rewriting Telegram handlers.

For Replit:
prepare project for an appropriate persistent/background deployment such as a Reserved VM/background worker if available on the account.

BUT:
If the current Replit plan does not permit a persistent deployment, DO NOT pretend the free development workspace is 24/7.

Instead:
- keep the project fully portable;
- explain clearly in README/report what production hosting is required;
- make deployment possible on another persistent Python host without code changes.

==================================================
29. SINGLE BOT INSTANCE
==================================================

Telegram long polling must not accidentally run twice with the same BOT_TOKEN.

Handle TelegramConflictError / duplicate polling gracefully and log a clear explanation.

Production should have exactly one polling worker.

Graceful shutdown:
close bot session
finish database operations.

==================================================
30. FSM / RESTARTS
==================================================

Current historical implementation used MemoryStorage.

It is acceptable for an unfinished calculation to be cancelled after a restart, provided:

- database data is never lost;
- inventory is never deducted for unfinished calculations;
- bot recovers cleanly;
- user can start again.

Do not make Redis mandatory merely for temporary FSM state.

However design the code so FSM storage could be changed later.
